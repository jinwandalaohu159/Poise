# Poise

让正在操作的程序始终反应迅速的 Windows 11 性能工具：后台让路的智能调度、一键清理、可还原的系统优化、按机型定制的硬件模式。

## 组成

| 部分 | 位置 | 说明 |
|---|---|---|
| 服务 | `service/crates/poise-service`（Rust） | 以 SYSTEM 身份运行，负责调度、清理、优化和硬件模式。所有改动都记入日志，可逐项还原；卸载时全部还原。 |
| 托盘代理 | `service/crates/poise-agent`（Rust，纯 Win32） | 用户会话中常驻（约 2 MB）：托盘图标与右键菜单；把用户桌面的状态（前台窗口、全屏、音频）上报给服务；按需启动界面。 |
| 界面 | `app/Poise.App`（C# / WinUI 3） | 主窗口与托盘面板。按需启动，都关闭后闲置 10 分钟自动退出。 |
| 界面逻辑 | `app/Poise.Core`（C#） | 与服务通信、文案表、状态换算、设置、日志；不依赖 WinUI，单元测试在 `app/Poise.Core.Tests`。 |
| 日志与记录 | `service/crates/poise-logbook`（Rust） | 日志系统与记录系统，独立于调度、在自己的线程里工作：调度只把事件和每轮摘要放进通道（不等待、不写盘），写日志、汇总使用记录、保存文件都在日志线程里做；界面看日志和记录时由它直接回答，不等调度引擎。 |
| 更新 | `service/crates/poise-update`（Rust） | 查询 GitHub 上的最新发布（托盘代理用）；更新助手 `poise-updater.exe`：下载、安装并重新启动新版本，显示进度。 |
| 安装程序 | `installer/`（Inno Setup） | 安装（可选位置）、升级、卸载。 |

服务与托盘代理、界面通过命名管道 `\\.\pipe\Poise` 通信。安装后，服务只接受与它位于同一目录（安装目录，只有管理员可写）的程序连接；托盘代理也只连真的服务：管道另一头必须是服务管理器里正在运行的 Poise 服务（普通用户打不开以 SYSTEM 运行的服务进程，所以问服务管理器，不读它的路径），连不上时把原因写进日志。服务启动时还没找到登录用户的，界面或托盘一连上就按它所在的会话补上，按用户保存的优化项不会因此显示成没优化。托盘代理与界面之间用命名事件（`Local\Poise.App.*`）通信。

文案表（`app/Poise.Core/Localization/Strings`）由界面、托盘代理和更新助手共用；后两者在编译时嵌入。

## 开发

需要 Rust（stable）和 .NET 10 SDK。

```powershell
# 服务：观察模式（只判断、不执行，不改动系统），数据放在 %LOCALAPPDATA%\Poise\dev
cd service
cargo run -p poise-service -- console

# 服务：真实执行（需要管理员权限）
cargo run -p poise-service -- console --live

# 托盘代理（另开一个终端）。开发时用 POISE_UI_EXE 指向调试版界面
$env:POISE_UI_EXE = "$PWD\..\app\Poise.App\bin\Debug\net10.0-windows10.0.26100.0\win-x64\Poise.exe"
cargo run -p poise-agent

# 界面：单独运行时打开主窗口；--flyout 打开托盘面板
cd app\Poise.App
dotnet build
.\bin\Debug\net10.0-windows10.0.26100.0\win-x64\Poise.exe
```

测试与检查：

```powershell
cargo test --workspace              # service 目录
cargo clippy --workspace --all-targets
dotnet test app\Poise.Core.Tests    # 界面逻辑与契约测试
```

改了服务返回给界面的数据结构时，先运行 `$env:POISE_UPDATE_FIXTURES=1; cargo test -p poise-protocol --test contract` 重新生成契约样本，再运行界面测试确认界面能读取。

日志：服务 `ProgramData\Poise\poise.log`（开发时 `%LOCALAPPDATA%\Poise\dev`；写满 2 MB 换成 `poise.1.log` 继续写），界面"日志与记录"页看的结构化日志在同一目录的 `events.jsonl`（满 1 MB 换成 `events.1.jsonl`），使用记录在 `records.json`（最多 200 条）；托盘代理 `%LOCALAPPDATA%\Poise\agent.log`，界面 `%LOCALAPPDATA%\Poise\app.log`。服务的一轮采样超过 150 毫秒时，日志会写明最慢的是哪一步，以及其中真正用掉的处理器时间（相差很多说明是在排队等处理器，而不是这一步本身慢）。

帧时间测量（判断 Poise 对游戏帧数的影响，管理员 PowerShell，首次运行自动下载 PresentMon）：同一游戏、同一场景各录一次，对比 `%LOCALAPPDATA%\Poise\frametime\summary.txt` 里的 1% 低帧、帧时间标准差和卡顿次数。

```powershell
.\scripts\frametime.ps1 -Process "game.exe" -Label off   # 先在托盘里退出 Poise
.\scripts\frametime.ps1 -Process "game.exe" -Label on    # 再打开 Poise
```

Poise 自身的原则：

- 不吃资源：服务和托盘代理以低于正常的优先级、效率模式运行在能效核上。一轮采样约 6 毫秒处理器时间，绝大部分是系统内核整理进程表（几千个线程）——采集、分类、调度本身合计不到 1 毫秒（三百多个进程时分类约 0.16 毫秒、调度约 0.13 毫秒：按进程号查表用更快的散列，进程名转小写走纯英文的快路）；各逻辑处理器的时间每轮只读一次（约 0.25 毫秒），整机占用和每个核心的负载都由它算出；处理器实际频率（性能计数器，每次 0.5～1.5 毫秒，系统忙时要两三百毫秒）在自己的线程里最多 4 秒读一次，采样只取最近的读数；刚有变化（前台切换、全屏切换、调整了程序）后 20 秒内或界面打开时每 2 秒一轮，其余时候每 4 秒一轮——游戏玩得正稳、重点程序稳定干活、全屏看视频时也一样（前台和全屏切换不等采样、立即重新调度），用户离开时每 6 秒一轮；暂停着（托盘代理没在运行）又没人看界面时每 10 秒一轮。界面开着但锁屏、离开超过 2 分钟、被别的最大化窗口完全盖住，或者开在另一个用户的会话里，都不算"界面打开"。用户离开、没在玩游戏时传感器读数放慢到 5 分钟一次；暂停期间电源守护 5 分钟才全面检查一次（电源计划 1 分钟看一次）。进程快照在引擎锁外采集，每轮锁住调度引擎的时间约 1 毫秒，前台切换和界面的请求不用等采集。服务每 30 分钟在日志里写一次自己的开销（每轮平均用时、处理器时间、最费时的一步）。界面每秒查一次的状态、程序列表、清理概览等只读请求，两轮采样之间直接给留着的回复，不在引擎锁里重新整理。设置、调整记录、运行过的程序交给后台线程写盘（变更日志除外：它必须先落盘再改设置）。界面不显示（包括被全屏游戏挡住）时停止刷新并进入效率模式，主页和走势图也不再重画；定时查询遇到上一次还没回来（服务忙）时跳过，不排队；列表按占用排序时，数值相近的行不来回换位；托盘代理只在桌面状态变化时上报（只报正在使用的那个会话：快速切换用户后不和另一个用户的托盘代理抢），睡眠醒来、解锁、切回这个用户时立即报一次；自己的会话没在使用时 30 秒才看一次，不查音频、不取状态，用户离开（锁屏）时也不取托盘状态；一键清理走单独的连接，清理期间会话状态照常上报；托盘代理连服务的线程一直及时运行（保活上报不在小核上排队），连不上时每 3 秒重连一次，醒来、解锁时立即重连，一次调用最多等 30 秒；托盘图标加不上（登录时任务栏还没准备好、资源管理器重启）时一直重试；托盘只解析状态里用得到的几项；界面改了语言、提醒圆点后托盘立即跟上；查询哪些程序在发声时复用音频设备（每次约 1 毫秒，而不是每次重新连接音频服务的 4 毫秒），查询在单独的线程里、最多等 1 秒（音频服务卡住时沿用上一次的结果，不拖住上报），某个音频设备出错时只跳过它。每轮采样与调度、界面请求这几个关键线程不降频、可以到任何空着的核心上跑一下，不在小核上排队。文本日志由单独的线程成批写入，写日志的线程从不等磁盘；给界面的回复只序列化一次，界面按行把字节直接读成结果（编译时生成的读写代码，不经过字符串和文档树）；服务没运行时界面隔一会儿（最多 2 秒）才再去连，不每次卡半秒，窗口重新显示时立即再试；握手成功、协议一致才算连上；一次调用最多等 30 秒，某个回复解析不了只算这次失败、不断开连接。界面以普通优先级启动（不继承托盘代理的"低于正常"）。一键清理不挡住整体状态的刷新；连着改几个优化项、程序类别时读取合并成一次，修改之前发出的读取结果不显示。程序图标只为显示出来的行读取；主页留在导航缓存里（换语言时重建），主页和托盘面板共用一份显示内容；整表重新排序时一次换上，例行刷新里的小幅变化不跑数字动画。
- 从不卡住调度：慢的操作都在各自的线程里——硬件控制（重新激活电源计划、BIOS 切换散热模式、风扇加速）、传感器读数、显卡占用测量（直接问显卡内核，开始测一个程序约 0.2 毫秒；受保护的进程才退回要 0.5 秒处理器时间的性能计数器）、读取程序的友好名称（访问磁盘）；电源模式滑块从注册表读，不调用要等几百毫秒的系统接口。电源设置的读取（当前电源计划、Poise 写入的值有没有被改掉、电源优化项还在不在）都在电源设置读取线程里：电源服务忙的时候（开机、刚切换模式）每次读取要几百毫秒，实测开机时一次检查要 2.6 秒，调度不再等它。切换模式只写变了的电源设置（按变更日志判断，不逐项读），也不再读回确认（以前切换一次要等 0.6～2.5 秒，游戏开局那一刻正好卡在这里）——真被别处改掉的由电源守护发现、改回；变更日志在调度线程里记好，所有电源设置的修改（切换模式、电源守护改回、应用优化项）真正写进电源服务、重新激活电源计划（电源服务忙时每项几十到几百毫秒）都交给电源执行线程，撤销也排在同一个队列里按先后写完；BIOS 切换散热模式、风扇加速在另一条线程里，两边互不等待。变更日志先落盘、再把写入交给执行线程，撤销的写入还没写下去时落盘的日志仍带着被撤销的条目，任何时刻断电、崩溃都能按日志还原；电源守护和优化项列表把还排着的写入当作已经写下，刚切换完模式不会误认成被改掉。第一次接管（登录、换了电源计划）要读的原值和当前计划也由电源执行线程预先读好（清空过的旧结果不会被收下），读好前每 0.5 秒看一次，读好就写；切换失败时隔得越来越久再试（最长 1 分钟）；暂停期间不再等预读。撤销没写成的电源设置（电源服务出错）留在变更日志里，原值不丢，之后还原时再试。Poise 退出时不等硬件还原完成，只有服务停止时才等（排着的电源设置最多等 10 秒、散热模式最多 5 秒）；调度引擎在别的线程里崩溃时先撤销调整再退出、交给服务管理器重启；电脑睡眠醒来时不把睡着的那段当成 Poise 已退出（只顺延睡前还新鲜的上报）。托盘代理断开了连接但进程还在时不立即暂停（按上报是否过期判断，重连后接着报就不暂停），它退出了（断开后 1.5 秒内结束）才立即撤销。服务已经暂停着时停止、关机也再撤销一次，暂停期间还有没撤销成的电源设置时每分钟再撤销一次（电源守护不再守它们），不留下没还原的设置。一键清理、列出优化项、刷新优化目录都在引擎锁外进行，界面的其他请求不排在它们后面。托盘代理与服务、界面与服务之间的每次调用都有超时，服务一时没有回应也不会把托盘和界面卡住（界面的实时数据和慢请求各用一条连接）。
- 少打扰硬件：机型接口（BIOS 的 WMI 方法）每次调用都可能让所有核心短暂停顿，界面不显示时 30 秒才读一次温度（玩游戏、有重点程序的状态来回切换也不多读）；玩游戏、有重点程序时完全不调用；散热模式和上次写入的相同时不调用；方法的入参定义只取一次（每次调用少两趟 WMI 往返）。NVIDIA 显卡的读数（NVML）只在独显醒着时读：先看显卡内核里的统计，Optimus 笔记本上休眠中的独显不会被叫醒。硬盘信息界面显示时 5 分钟、后台半小时刷新一次，后台不读温度和磨损（会唤醒休眠中的机械硬盘、移动硬盘）。显卡驱动还没就绪（开机时）就隔一会儿再试，不会一次失败就再也不读显卡。
- 不和硬件抢方向盘：不按温度切换模式（处理器和显卡到了上限会自己降频保护）。
- 异常退出也能复原：调整过哪些进程记在 `ProgramData\Poise\adjusted.json`，服务崩溃或被强行结束后，下次启动把还在运行的那些进程恢复原样。戴尔机型接管前的散热模式在换掉之前记在 `ProgramData\Poise\thermal.json`，异常退出后下次启动先还原（记录里的取值不在 BIOS 列出的模式里时不用）；Poise 退出期间用户在 AWCC 里换的模式，服务停止时不再改回。风扇加速设为 0 时不碰风扇，只有 Poise 加过速才会收回；睡眠醒来后核对一次散热模式和风扇加速，被 BIOS 改了就重新写入；切换散热模式失败（WMI 一时不可用）时 30 秒后再切一次，WMI 服务重启后自动重新连接散热接口。数据目录每次启动、打开里面任何文件之前先收紧权限：所有者改为管理员组，指向别处的链接删掉，别人事先放进去的文件改名为 `*.untrusted`、不再使用（不删除，万一是真的记录还能找回），这样的目录删掉，以 SYSTEM 运行的服务不会按伪造的记录做事；收紧不了时服务不启动。变更日志读不到（被别的程序独占）时先重试，还读不到就不做任何修改、也不保存，免得覆盖里面的原值；保存失败时这次的电源设置不写；有读不懂的条目（降级后遇到新版本记的）时只跳过那几条、原样保留；替换文件写透到磁盘，解析不了的文件带上时间改名保留。服务崩溃时把原因写进日志，并由服务管理器自动重启（正常停止报告成功，不会被重新拉起；安装程序停服务前先关掉"正常退出也重启"，从 0.8.0 也能顺利升级）；关机时在预关机通知里就撤销调整、还原散热模式，不等到别的系统服务都停了。

核心分配：按处理器自己报告的拓扑划分"核心域"——效率等级相同、共用一块缓存的核心（大小核处理器：大核一个域，小核按共用的二级缓存每 4 个一组；多 CCD 的锐龙：每个 CCD 一个域，带 3D 缓存的优先；只有一块缓存的处理器不限制核心）。同一个程序的所有进程放在同一个域里，线程之间共享的数据留在同一块缓存里。

- 重点程序：正在玩的游戏，以及正被直接使用、持续需要处理器的任何程序（前台的编译、渲染、导出，临时全速、设为始终优先的程序）。持续干重活要满 8 秒（平滑后的负载）才算，打开网页、点开聊天窗口这类几秒钟的忙不算；像游戏的程序等了一分钟还确认不了（全屏看视频、可视化程序）就不再按等待确认的游戏放到大核，负载在门槛附近抖动时也不来回翻转；标为游戏的程序里的子进程不另算一个游戏；切出去看一眼消息、通知弹窗抢走前台，15 秒内回来、负载还在就仍是重点程序，不来回切换。像游戏的程序（前台全屏、显卡在渲染）还要确实在用处理器才先放到大核，持续用不到五分之一个核心的（全屏看视频）也不会被确认为游戏。同时有几个重点程序时按它们加起来的负载一起放开核心。在命令提示符里跑的编译（主进程不参与调度）按树里参与调度的进程判断。它先占主域（大核）；需要的线程更多时逐个加上副域，直到全部核心——按持续的负载（最近两轮里较低的）放开、每轮最多放开一级，回落后保持一会儿才逐级收回。一个域能承担多少按物理核心算（超线程只算四分之一个核心），只有两三个大核的处理器不把重点程序限制在大核上。像游戏的程序不等确认就先放到大核。
- 有重点程序时，其余没在用的程序让到副域（小核），只挪核心，不降优先级、不节能（游戏立即这样做；前台的编译、导出这类重点程序要持续一分钟，短的增量编译只自己用大核，不为它把所有程序挪走再挪回来）；各程序按负载分摊到各组小核，分到哪组就留在哪组，重点程序借用的那组会空出来。重点程序结束一会儿后（游戏按整个游戏会话）移回。

后台让路：按程序（整个进程树，中间的进程退出了也照样归原来的程序）判断，只在正在用的程序需要处理器时才让持续占用处理器、或持续大量读写磁盘（同步、下载、备份）的后台程序让路；后台自己把整机跑满不算有人需要。让路分两档，用户一点开就立即恢复：

- 只降优先级：正在用的程序在忙时。降低优先级、内存与磁盘读写优先级（Windows 不会因为程序在后台就降低这些），核心不限、不节能——正在用的程序需要时优先，其余时间空闲的核心照样给它用。
- 完整让路：有重点程序、处理器没有余量（处理器自己报告被限速；读不到限速信号时看温度，温度到了临界也算）、用电池时，以及用户设为"低优先级"的程序。温度高本身不算：不同处理器的温度上限不同，笔记本处理器在高性能模式下本来就工作在 90～100°C。再移到小核、开启效率模式（同时不理会它请求的高精度计时器）。负载轻的（达不到平时的门槛：手柄与按键映射、头部追踪、录像、副屏上的视频）只移到小核、降优先级，不开效率模式——那会让输入变迟、画面掉帧。用户离开超过 5 分钟（游戏挂在菜单里），需求不再因为游戏保持在"高"。

- 不来回调整：让路后闲下来也保持；没人需要处理器一段时间后，已经闲下来的恢复，还在忙的只留着"低于正常"（不限核心、不节能，没人抢处理器时不影响它的速度），不在用户一走一回之间来回调整；刚用过的程序（离开前台、停止发声……）20 秒后才会再让路或挪到小核，来回切换窗口、通知弹窗抢一下前台都不会让它反复调整。"刚用过"只保持最近 3 个参与调度的程序：点一下开始菜单、资源管理器、任务管理器不占名额，退出了的程序立即让出名额。
- 前后一致：有重点程序时按更低的门槛让路的程序，之后如果已远低于新的门槛就恢复，依然很忙的降回"只降优先级"。
- 正在发声的程序不让路，其中真正输出声音的进程不受系统节能限速；有重点程序时又很忙，只挪到小核。正在用麦克风的程序（通话、直播、录音）没人说话时也算在发声。
- 商店（UWP）程序按它自己的进程算前台和窗口，不会因为窗口由系统托管而被当成后台程序。
- Windows 自己的维护程序（更新安装 TiWorker、搜索索引、兼容性评估、.NET 预编译、恶意软件删除工具、磁盘优化），以及装在 Program Files 里的后台更新程序（Office 即点即用、Edge 与 Chrome 的更新、Firefox 维护服务、Adobe 更新）：有重点程序、并且它们没在被使用时挪到副域、降低内存与磁盘读写优先级，不改优先级、不节能、不重启；Windows 的只认 Windows 目录下的。其余系统进程一律不碰。
- 撤销调整时回到程序自己原来的设置：程序自己开过效率模式（浏览器给后台标签页的进程）或设过核心范围的，撤销后还是它自己的设置；调整期间它自己又改过的，以它的为准。
- 调整前核对进程身份（进程号会被新进程复用），对不上就当已退出，绝不动到别的程序；执行失败的调整隔一会儿再试（4 秒起，逐次加倍，最长 5 分钟），不每轮重复。
- 每次让路、恢复、需求变化、重点程序占用的核心变化、游戏退出都记一条日志，写明程序、负载（处理器、磁盘）和原因（在前台、刚用过、在发声、没人需要处理器、需求降低、像游戏等待确认、负载降下来了、离开前台……）；需求变化写明从哪来（有重点程序、处理器没有余量、正在用的程序在忙、用电池）；挪到小核的闲置程序汇总成一条；进程树变化让同一个程序时隐时现时不重复记录；退出的游戏仍写出名称。

界面的两个面板（主页下方进入）：

- 核心与缓存：共用一块三级缓存的几组核心圈在一起，每组写明二级缓存（每个核心独享，或几个核心共用）、负载，画出每个物理核心和它的线程（按占用填色，每 2 秒刷新），列出 Poise 放在这组核心上的程序（游戏、重点程序、让路、挪开）；大核每组占一整行，小核组在宽窗口里两列并排；另列没有限制核心、负载最高的程序（由 Windows 安排）。Windows 不提供每个程序占用多少缓存，所以按核心说话：放在同一组核心的程序共用这一组的缓存。大小核、多 CCD、只有一块缓存的处理器各有合适的叫法。只取服务已有的结果，不额外采样；处理器结构只建一次，之后原地更新。
- 日志与记录：日志按调度、模式、电源与优化、清理、Poise 分类，写明做了什么和原因（负载、在前台、在发声……），可以打开详细日志的文件夹；只有显示着的标签在读取（日志每 2 秒只取新增的几条，记录每 20 秒、没变就不动列表），日期与时刻单独一列、各行对齐；使用记录是每段有重点程序的时间（玩游戏、编译、渲染）一条：哪些程序、多久、用过的模式、用了哪些核心、挪开和让路了多少程序、处理器平均与最高的占用和温度、被限速多久。

游戏调度：游戏（自动识别的或标记的）按重点程序分配核心、不受系统节能限速，标记的游戏优先级高一级；玩游戏时后台更早让路（刚用过的客户端也不再豁免）；全力 / 极限模式只让大核全速，小核保持均衡的能效偏好，把功耗和温度留给游戏；几组大核缓存大小不同的处理器（7950X3D 这样一组带 3D 缓存）保留出厂的核心停放，处理器驱动靠它把游戏留在缓存大的那组上；一局结束后游戏模式、后台让路保持 3 分钟，局间不来回切换。

## 构建与安装

```powershell
.\scripts\package.ps1      # 构建并生成安装程序 dist\Poise-Setup-<版本>.exe（加 -SkipBuild 只打包），不改动系统
.\scripts\build.ps1        # 运行测试，发布版输出到 dist\Poise，不改动系统
```

- 安装程序用 Inno Setup 6.7+ 编译（`installer/Poise.iss`；`winget install JRSoftware.InnoSetup`）。向导跟随系统的浅色 / 深色外观，按系统语言显示中文或英文；向导图片由 `python scripts/make-installer-images.py` 从 `icon/foam.png` 生成。
- 首次安装可以选择安装位置（默认 `Program Files\Poise`，不能放在用户文件夹里）；安装目录的权限会设为只有管理员可写——服务以 SYSTEM 身份运行，不能让别人替换其中的程序。再次运行安装程序即为升级：沿用上次的位置，只替换文件、更新并重启服务，保留设置、开机启动选择与优化记录。
- 服务的注册、首次安装时开启开机启动、卸载时还原系统修改，都由 `poise-service install / uninstall` 完成；安装程序只负责文件、快捷方式（开始菜单，可选桌面）和"设置 → 应用"里的登记。全程不出现控制台窗口。
- 开机启动是任务计划程序里 `\Poise\` 文件夹下的登录任务（定义见 `app/Poise.Core/Settings/AutostartTask.xml`，界面和安装共用），登录后立即启动托盘代理；不用 Run 键，因为 Windows 会把 Run 键里的程序推迟一两分钟。
- 普通用户输入管理员密码安装、卸载时，开机启动开给、按用户保存的修改还原到正在用电脑的这个用户（不是输入密码的管理员）。
- 安装程序按服务的实际状态停止服务、等它真正停下（最多 1 分钟）；停不下来就不安装，原来的版本保持不变；安装没有完成（回滚）时把原来的服务恢复启动。自动更新时安装日志保存在下载的安装包旁边。
- 卸载：在"设置 → 应用"里卸载 Poise。还原所有系统修改、删除服务、所有用户的开机启动任务、程序、记录与日志；如有修改没能还原（或者服务没有及时停下），修改记录保留在 `ProgramData\Poise`，重启后重新安装再卸载即可重试。
- 发布：在 `service/Cargo.toml` 里改版本号，运行 `package.ps1`，再用 Project Hub 把安装程序发布到 GitHub Releases（标签 `v<版本>`，附件 `Poise-Setup-<版本>.exe`）。
- 自动更新：界面运行时启动后检查一次、之后每小时一次，托盘代理在后台定时检查；有新版本时托盘提醒，设置页"更新"里可以检查更新、立即更新。点"立即更新"后由更新助手 `poise-updater.exe`（复制到 `%LOCALAPPDATA%\Poise\updates` 运行）接手，界面退出：它在一个进度窗口里先下载安装程序（核对大小和 GitHub 提供的 SHA-256），再静默安装（会请求管理员权限）、等服务启动、重新启动托盘代理，完成后自动关闭；失败时说明原因，原来的版本保持可用。日志在 `%LOCALAPPDATA%\Poise\updater.log`。开发版本（没有 `version.txt`）不检查更新。
- 安装包未签名（没有代码签名证书），首次运行可能出现 SmartScreen 提示。
- 图标的原图是 `icon/foam.png`。更换后运行 `python scripts/make-icons.py`（需要 Pillow），重新生成 `app/Poise.App/Assets` 下的程序图标、托盘提醒图标和界面标志，再构建即可。

## 安全边界

- 对游戏只做任务管理器同等级别的操作（优先级、CPU 核心、效率模式）；不注入、不读写游戏内存、不 Hook、不修改游戏文件、不模拟输入；反作弊程序及其服务永不触碰——名单里的程序、与它们装在同一目录的程序（同一套反作弊往往有好几个程序）、装在已知反作弊目录里的程序都算。
- 不安装驱动；不关闭 Defender、防火墙、UAC、Windows 更新、内存完整性。
- 联网只为更新：界面和托盘代理访问 GitHub 查询最新版本、下载安装程序（校验 SHA-256），不上传任何数据；服务（SYSTEM）从不联网。
- 服务只执行固定的操作集合；管道有访问控制并拒绝远程连接；配置与日志只有管理员可写；重启用户程序时使用用户自己的身份。
- 戴尔 / 外星人机型（BIOS 有 AWCC 接口的，按接口判断，不看型号）的散热模式只使用 BIOS 自己列出的模式：安静 → 0xA3，全力（接通电源时）→ 0xA4（BIOS 列出时）或 0xA1，均衡 → 回到用户原来的模式（启动时的模式，可以是 G 模式；运行期间在 AWCC 里换过的以用户的为准）；服务停止或卸载时恢复原模式。
